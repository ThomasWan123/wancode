# v0.19 post-start session stall

Date: 2026-08-09
Status: **P1 fix verified in a rebuilt release-mode desktop candidate; integration pending**

## Observation

The exact `0b86c77` release executable was opened on the normal Windows 11
profile. A new Code session remained on `Starting...` for more than 20 seconds.
Changing the visible surface and selecting DeepSeek V3 did not enable the
composer, so no provider request was sent.

The durable backend evidence contradicted a provider failure:

- session `019fe662-3124-7311-ac3c-004781cb996a` was created for the expected
  workspace;
- `summary.json` recorded zero messages and the configured catalog model
  `glm-5.2`;
- all three MCP servers reached `mcp_server_connected`, followed by healthy
  checks and a successful `mcp_init_completed` event;
- the unified log recorded `session created` and no inference failure for this
  session;
- the process closed cleanly and the crash marker recorded `cleanExit=true`.

This proves the attempt did **not** test DeepSeek behavior. The request never
left WanCode.

## Root-cause analysis

After publishing the session handle, the Code startup path synchronously waited
for `x.ai/skills/refresh-baseline`. The surrounding comment described that
refresh as best effort, but the request had no timeout. A missing reply could
therefore keep the Tauri `agent_start` invocation pending indefinitely while
the engine session and MCP clients were already healthy. The frontend clears
`starting` only in the invocation's `finally` block, matching the observed
state exactly.

## Remediation

Local commit `595c054` changes the refresh to a detached post-start maintenance
task with its own five-second timeout and diagnostic warning. Session creation
no longer waits for the maintenance request. A regression test holds the ACP
receiver open without replying and verifies the refresh terminates within the
test deadline.

Validation against the current engine worktree:

- focused non-responsive refresh regression: PASS;
- combined PR #28 plus startup-fix library suite: **181 passed, 0 failed, 1 intentionally ignored**;
- WanCode-only Clippy with `-D warnings`: PASS.

## Rebuilt desktop acceptance

The fix was combined with PR #28 in detached validation commit `6767ea4` and
built as a release-mode Windows executable against engine `2f480062`. The
candidate was launched with an isolated `GROK_HOME` and the real app data root,
using workspace `qa-user-fixtures/b02-failing-test`.

The same Code journey now returned from `Starting...` to `Connected` in under
seven seconds. Session `019fe6b0-be46-7e13-bf76-e6440dd659d8` then completed
three real-provider turns without tools:

| Model | Prompt contract | Result |
|---|---|---|
| Zhipu GLM-5.2 | exact `WANCODE-STARTUP-PASS` | PASS |
| DeepSeek V3 | exact `DEEPSEEK-V3-PASS` | PASS (about five seconds) |
| DeepSeek R1 | exact `DEEPSEEK-R1-PASS` | PASS (about eight seconds) |

The executable remained connected throughout model switching and exited
cleanly. SHA-256 was
`8C77CE1ECDDA117CFDCB2E89C1BE5692698B6D704E9499DC8FD96E325F98EF39`;
Authenticode status was `NotSigned`.

After verification, the isolated engine test root and the two test-created
surface bindings (`019fe6ad-742e-7951-87cb-19e5b37848d5` Chat and the Code
session above) were deleted. Existing user bindings and retained orphan samples
were not changed.

## Remaining acceptance gate

Desktop behavior is verified locally, but the fix is not release-integrated.
Its branch must be reviewed, merged, and pass exact-head CI. Signing, packaged
installer validation, and clean Windows 10/11 coverage remain independent
release gates.
