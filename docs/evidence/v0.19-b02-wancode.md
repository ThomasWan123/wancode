## Fixture and task

The disposable Git fixture contained a two-function JavaScript cart module and
three Node test-runner tests. The only failing contract required a 15% discount
on `19.99` to preserve currency precision and return `16.99`. Production code
incorrectly used `Math.floor`, returning `16`.

The exact user task in each fresh session was:

> Run npm test, diagnose the failure, make the smallest correct production-code
> fix, do not modify tests, rerun the full test suite, and summarize the result.

The fixture began at a clean Git commit and the same failing production source
was restored before every run.

| 3 | PASS | One production line | 3 pass / 0 fail | ~41 s | Used `cmd /c "npm test 2>&1"` |

Median observed elapsed time: approximately **41 seconds**. Timing came from
the bounded GUI observation loop and is suitable for task-level comparison, not
microbenchmarking.

Every run made the same minimal production change:

```diff
-  return Math.floor(total * (1 - percentage / 100));
+  return Math.round(total * (1 - percentage / 100) * 100) / 100;
```

Independent post-run verification confirmed that only `src/cart.js` was dirty,
`test/cart.test.js` was unchanged, and `node --test` passed all three tests.

## Product observations

1. The Code surface exposed its tool steps, automatic approvals, patch, and test
   evidence clearly enough to audit the result.
2. Windows execution recovery was correct in all runs, but chose three different
   equivalent command forms. A single platform-aware command normalization layer
   would reduce latency and behavioral variance.
3. Creating a fresh session clears the active workspace and requires selecting
   the same project again, despite the workspace remaining visible in the lower
   switcher. This is measurable repetitive friction versus coding products that
   retain the active project when starting another task and should be evaluated
   as a P2 UX candidate rather than treated as an automatic defect.
