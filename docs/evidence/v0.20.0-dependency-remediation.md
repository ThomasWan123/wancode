> 复核对象：[#68](https://github.com/ThomasWan123/wancode/pull/68) 提出的 P1「依赖安全签核失败」
> 复核日期：2026-08-20
> 基线：`origin/main` `52453f2`（已发布的 v0.20.0）；分支 `fix/v0200-dependency-advisories`。
> #68 的更新器混沌加固尚未合入主干，**不在**本次构建基线内——同一个版本号下

## 1. 复核结论：P1 成立，但计数口径需要收紧

独立在真实工作区根 `grok-build`（wancode 是它的 workspace member，
`Cargo.lock` 在那里，不在 `src-tauri/`）重跑 `cargo audit`，确认原报告的
**11 个命中 / 7 个公告**属实。

原报告的定界有一处需要修正：它只区分了「是否出现在 Windows 目标解析中」，
没有区分「是否有任何 crate 真的依赖它」。逐条用
`cargo tree -p wancode -i <spec> --target x86_64-pc-windows-msvc` 复核后：

| 公告 | 包 | 进 Windows 二进制？ | 归属链路 |
|---|---|---|---|
| RUSTSEC-2026-0204 | crossbeam-epoch 0.9.18 | 是 | crossbeam ← xai-codebase-graph ← 引擎 |
| RUSTSEC-2026-0258 | h2 0.4.15 | 是 | hyper ← reqwest ← 引擎 |
| RUSTSEC-2026-0257 | webbrowser 1.0.6 | 是 | xai-grok-mcp ← 引擎 |
| RUSTSEC-2026-0194/0195 | quick-xml 0.37.5 | 是 | **wancode 直接依赖**（`src-tauri/Cargo.toml`） |
| RUSTSEC-2026-0194/0195 | quick-xml 0.38.3 | 是 | 引擎 workspace 根清单钉死 `quick-xml = "0.38"` |
| RUSTSEC-2026-0194/0195 | quick-xml 0.39.4 | 否 | pdf_oxide（升级后改走 wayland 链，见下） |
| RUSTSEC-2026-0185 | quinn-proto 0.11.14 | 否 | **全 workspace 全 target 全 kind 无父节点** |
| RUSTSEC-2023-0071 | rsa 0.9.10 | 是 | jsonwebtoken ← gcloud-auth ← gcloud-storage ← 引擎 |

`quinn-proto` 那条特别值得记一笔：`cargo tree --workspace -i
quinn-proto@0.11.14 --target all -e normal,build,dev` **没有任何输出**——
不是"Windows 上不用"，而是整个工作区没有任何 crate 依赖它，它只是被某条
未启用的可选 feature 路径留在 lock 里，不参与任何编译。

## 3. 升级踩到的真 bug：DOCX 实体引用会被静默吞掉

quick-xml 0.41 改了事件模型：`&amp;`、`&#x41;` 这类引用不再由 `Event::Text`
内联展开，而是各发一个独立的 `Event::GeneralRef`，`BytesText::unescape`
随之移除。

只做最小编译修复（`unescape` → `xml10_content`）会让 `parse_document_xml`
的 `_ => {}` 分支吃掉 `GeneralRef`，于是 DOCX 里的「甲&amp;乙」被静默抽成
「甲乙」。这属于 [`work_docx.rs`](../../src-tauri/src/work_docx.rs) 文件头
①/④ 一直在挡的**静默丢正文**，只是换了个入口——而且 `runs` 仍然铺满、
`is_well_formed()` 仍然为真，19 条既有测试**一条都测不出来**。

处置：新增 `Event::GeneralRef` 分支，补回定界符后交
`quick_xml::escape::unescape` 展开（数值引用自行计算，五个预定义实体自行
识别，其余一律 `UnrecognizedEntity` → 整篇拒收）。DOCTYPE 已在上游分支拒掉，
合法 DOCX 中不存在自定义实体，fail-closed 是正确口径。文件头新增第 ⑥ 条
记录这个陷阱。

## 5. 补上两道门——此前 CI 根本没有 `cargo audit`

原报告把依赖审计当成一次手工检查。事实是：CI 里**完全没有**依赖公告检查，
"依赖安全"全靠人想起来手跑一次。那不是门，是习惯。本次补两道：

### 5.1 依赖公告门（常驻 job）

`scripts/dependency_advisory_gate.ps1`，ci.yml 新增 `dependency-advisory` job。

不用 `cargo audit --ignore`：那是按公告号整条静音，同一个公告日后命中到别的
包、别的版本、别的链路一样不响。本门绑 **(公告号, 包名, 版本)** 三元组，
且**双向**断言：

* 命中了但没申报 → 红（不许静默新增暴露面）；
* 申报了但已不再命中 → 也红（豁免必须随修复一起删，不许留僵尸条目）。

只拦 `vulnerabilities`；`unmaintained` / `unsound` / `yanked` 归 `warnings`，
只统计不拦截——避免把"警告很多"和"有已知漏洞"混成一句话。

| 检查 | 含义 |
|---|---|
| A1 | `cargo audit --json` 可解析（不可解析立即红，不许继续判绿） |
| A2 | 申报文件五列齐备、理由码在固定集合内、复核日期可解析 |
| A3 | 无未申报命中 |
| A4 | 无僵尸豁免 |
| A5 | 审计对象确实是 vendored 引擎 lock |

**负向门测试** `scripts/test_dependency_advisory_gate.ps1`：**9/9 场景符合预期**
（含 1 个正向对照）。CI 里负向测试排在门之前跑——顺序反过来的话，一道恒绿的
门也能"通过"。

### 5.2 迁移审计新增 `security-upgrade-delta` 模式

既有五种模式没有一种能表达"升级既有依赖"：`dependency-delta` 的 D3 明确
要求「既有 package 一个没少、没改版」，而安全升级的定义就是既有 package 换
版本，正好撞在 D3 上。硬套只能靠放宽断言蒙混，那等于把门拆了。

新增 S1–S10（`scripts/migration_audit.ps1`）：

| 检查 | 含义 |
|---|---|
| S1 | 引擎 commit 未变 |
| S2 | 有效树里只有 `Cargo.lock` 变 |
| S3 | 每一处版本变化都是**升级**，无降级、无包被删（语义化版本比较，不是字符串比） |
| S4 | 升级集合与申报逐字相等 |
| S5 | 新增包集合与申报逐字相等 |
| S6 | 每条升级绑一个 RUSTSEC 编号（多条用 `+` 连接）或显式标 `collateral` |
| S7 | 不得新增 `*-sys` **包名**（既有 `-sys` 包多一个版本不算） |
| S8 | wiring patch 未变 |
| S9 | 三处哈希已登记 |
| S10 | lock 中 wancode 版本 == 应用版本 |

实跑结果：**十项全 PASS**（7 处升级，17 处新增，无降级无删除）。

S5 的门确实会咬人——申报行留 `PLACEHOLDER` 时该项 FAIL 并打印出完整的
observed/declared 对照，填上真实清单后转 PASS。

## 8. NOT-RUN / 已知缺口

* **`security-upgrade-delta` 没有专属负向门测试。** S5 有一次真实的
  FAIL→PASS 实证（`PLACEHOLDER` 那轮），但没有像 `test_audit_negative.ps1`
  那样的可重复夹具。这与既有的 `dependency-delta` / `wancode-lock-delta` /
  `version-only` 三种模式**同等**——它们同样没有负向测试。要补就三种一起补，
  另案。
* **`rsa` 的真解未做。** 换掉 gcloud 依赖链不在本次范围。
* **未验证升级后的运行时行为面。** 单测与构建通过不等于 `webbrowser 1.2.4`
  / `plist 1.10` / `taffy 0.12` 在真实交互路径上无回归；打包后的真机验收另计。
* 原报告中的竞争能力门（B01–B10）、环境矩阵、真实恶意 HTTP 夹具等
  `NOT-RUN` 项，本次未触碰，仍以 [#68](https://github.com/ThomasWan123/wancode/pull/68)
  的 `v0.20.0-post-release-matrix.md` 为准（该文件在 #68 分支上，未合入主干，
  故本分支不含它，正文里不做仓内相对链接）。
