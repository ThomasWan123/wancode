# WanCode v0.19 packaged crash-recovery attempt

Date: 2026-08-09  
Product candidate: `0b86c77bce151fd447f23c47e3b28d3986d54577`  
Result: **PARTIAL PASS FOR THE RELEASE BINARY; INSTALLED-PACKAGE GATE REMAINS OPEN**

## Objective

Create a real session, force-terminate WanCode after the first successful turn,
then launch the installed release candidate and verify that the recovery banner
restores the exact session before the dirty marker is acknowledged.

## Isolation

The attempt used the disposable root `D:\WANCode\qa-crash-e2e` and isolated all
application-controlled state:

- `GROK_HOME`;
- `APPDATA` and `LOCALAPPDATA`;
- `TEMP` and `TMP`;
- the WebView2 user-data directory;
- the AUTOTEST workspace and surface-binding store.

The real model configuration was copied into the isolated engine home. Its
contents and credentials were not printed. No real user session or sidecar was
modified.

## Observed result

The current-head debug executable was launched from a clean Windows PowerShell
process with a canonicalized `Path`. WebView2 initialized a complete isolated
profile, proving that the GUI process started and reached browser-runtime
initialization. However, during the 181.4-second bounded run:

- no `wancode-autotest.log` file was created;
- no `SMOKE S1-start PASS` event was emitted;
- redirected stderr remained empty;
- no session directory, dirty recovery marker, or binding was created;
- the exact launched process was force-stopped at the bound, and no WanCode
  process remained.

PowerShell 7, which is the documented smoke launcher, was not installed or on
`PATH` on this host. Re-running the same bounded helper under Windows
PowerShell produced the result above. Repeated attempts were stopped to avoid
turning an ambiguous harness condition into a product verdict.

A separate minimal child-process probe used the same Windows PowerShell
`Start-Process` pattern after canonicalizing the duplicate `Path`/`PATH`
entries. The child observed both the exact `WANCODE_AUTOTEST` value and the
isolated `TEMP` value. The debug executable also contains the compiled
`WANCODE_AUTOTEST`, `SMOKE BEGIN`, and log-path strings. This rules out silent
loss of those two environment variables and a stale binary as explanations.
The unresolved interval is narrower: the process initialized WebView2 but did
not reach or schedule the Tauri `.setup()` AUTOTEST task on this launch path.

## Interpretation

This run does **not** prove a recovery defect: it never reached the precondition
of a durable dirty session. It also does not satisfy the packaged recovery
gate. The transaction-level frontend and Rust tests remain valid, but release
GO still requires an end-to-end forced-crash run on a host where the official
launcher enters AUTOTEST, followed by recovery through the exact packaged
candidate.

## Release-binary recovery follow-up

The exact unsigned release executable built at `0b86c77` was then launched in
the normal user context. It presented the visible recovery banner:

> Looks like the last run ended unexpectedly. Restore that session?

Windows UI Automation exposed the banner text and distinct `Restore` and
`Dismiss` buttons. Activating `Restore` produced the following bounded result:

1. the composer entered `Starting...` while the banner remained visible;
2. within eight seconds, the application reported `Connected` and the banner
   disappeared;
3. the selected session was
   `019fe5fc-19ad-79c2-9147-265d1ebf2c2b` in
   `D:\WANCode\qa-user-fixtures\b02-failing-test`;
4. after a graceful `Alt+F4` close, no WanCode window remained;
5. the durable marker named the exact same session and workspace, had
   `cleanExit=true`, and the session existed in one engine directory with one
   `chat_history.jsonl` containing two lines.

This is direct evidence that the release binary can expose the recovery action,
hold the prompt while restoration is in progress, restore the exact durable
session identity, and acknowledge clean exit after a successful restore. The
pre-existing recovered session had only a minimal two-line history, and the raw
dirty marker was not snapshotted before launch. This therefore remains a
partial result: it does not prove rich-history fidelity, restore-failure retry,
or behavior from an installed and signed package under isolated roots.

## Required rerun

1. Use PowerShell 7 and the exact release-SHA smoke launcher to create and
   snapshot a controlled dirty marker before launch.
2. Assert the first successful turn, durable session directory, binding, and
   `cleanExit=false` marker before termination.
3. Launch the installed, signed candidate with the same isolated state.
4. Verify the visible recovery prompt, exact session identity and history, a
   retryable failure path, and `cleanExit=true` only after successful restore or
   explicit dismissal.
5. Preserve process output, marker transitions, screenshots, and artifact
   hashes in the release evidence bundle.
