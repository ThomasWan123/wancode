# WanCode v0.19+ Product Quality and Competitive Test Plan

> Baseline: WanCode v0.19.0 (`251f34b` release, `43fb87b` documentation refresh)  
> Plan owner: Product Quality  
> Benchmark snapshot: 2026-08-09  
> Review cadence: every minor release and whenever a benchmark product changes a relevant workflow

## 1. Executive quality objective

WanCode should not win by copying every visible feature from ChatGPT or Claude Code. It should win by being the most dependable Windows desktop agent for users who need:

- first-class choice among Zhipu GLM, DeepSeek, and OpenAI-compatible providers;
- a strict, session-bound boundary between safe general Chat and full-power Code;
- a visual local workflow for repository work, Git, review, terminal, MCP, hooks, skills, subagents, and recovery;
- fail-closed behavior when identity, policy, model capability, or provider routing is uncertain;
- reproducible engine inputs and signed, recoverable application updates.

The test program therefore measures outcomes, not feature count. A capability is not considered shipped until its success path, denial path, recovery path, and user-visible failure path have evidence.

## 2. Competitive reference model

The comparison below uses current official product documentation, not remembered behavior.

- OpenAI documents separate Chat, Work, and Codex experiences in the desktop app. Chat covers conversational assistance, Work covers longer deliverables, and Codex covers repository and developer-tool workflows. Local and cloud behavior differ by surface and plan.
- OpenAI also documents Projects, scheduled work, apps/connectors, a built-in browser, local folders, voice, and explicit permission controls for external actions.
- Anthropic documents Claude Code as a local coding agent with permissions, project instructions, MCP, hooks, skills, subagents, background work, checkpoints, non-interactive use, and local session recovery. Claude Code on the web adds isolated asynchronous tasks and pull-request delivery.
- Claude Desktop Cowork and Claude Code can optionally use browser or computer interaction, subject to product availability and explicit permissions.

### 2.1 Outcome comparison

| User outcome | ChatGPT desktop | Claude / Claude Code | WanCode v0.19 | Test implication |
|---|---|---|---|---|
| Fast general assistance | Chat | Claude chat | Chat | Measure first-response reliability, image handling, web grounding, and zero local-extension leakage. |
| Local repository development | Codex | Claude Code | Code | Use the same task fixtures and require verifiable diffs and tests. |
| Long-running knowledge work | Work | Cowork | Planned | Do not claim parity; define entry criteria before implementation. |
| Local tools and extensions | Apps/plugins and Codex tools | MCP, hooks, skills, plugins | MCP, hooks, skills, plugins in Code | Prove Code remains complete while Chat remains empty for its whole lifetime. |
| Browser-assisted verification | Built-in browser / Chrome path | Browser / computer use where available | Local preview plus system browser | Treat full browser automation as a product gap, not a v0.19 release defect. |
| Checkpoint and recovery | Conversation/task history | Checkpoints and `/rewind` | Conversation/files/both rewind | Stress destructive and interrupted recovery paths. |
| Parallel work | Work/Codex tasks | Subagents, background work, web tasks | Subagents, background tasks, worktrees | Verify isolation, attribution, cancellation, and merge safety. |
| Provider choice | OpenAI models | Anthropic models and supported enterprise backends | GLM, DeepSeek, compatible endpoints | This is a differentiator; provider routing must be a P0 contract. |
| Desktop administration | Workspace roles and app permissions | Managed settings and permissions | Local configuration | Prioritize transparent local state, exportable diagnostics, and safe defaults. |

### 2.2 What WanCode should deliberately emphasize

1. **Provider independence with evidence.** A selected catalog entry must route to its own endpoint and credential, including restore and hot-switch paths.
2. **Surface identity, not cosmetic modes.** Chat and Code are immutable session identities enforced by the Rust backend and engine handshake.
3. **Windows-native operational safety.** Signed updates, Job Object process-tree cleanup, crash recovery, and visible approval states should be tested as a coherent lifecycle.
4. **Auditable local workflows.** Diff review, Git root pinning, worktree conflict checks, snapshots, and rewind provide evidence a user can inspect.
5. **Fail-closed compatibility.** Unknown model capability, malformed sidecars, future schemas, unsupported provider responses, and policy conflicts must block or visibly degrade; they must never silently broaden access.

## 3. Scope and non-goals

### 3.1 In scope

- released Chat and Code surfaces;
- onboarding, provider setup, capability resolution, and model switching;
- session create, restore, fork, review, worktree, subagent, and crash recovery;
- tool approvals, file changes, terminal, Git, MCP, hooks, skills, plugins, LSP, and image routing;
- frontend state, keyboard behavior, international input, accessibility, and visual feedback;
- performance, resource use, interruption, concurrency, update, and rollback;
- packaged Windows x64 builds and supported upgrade paths;
- competitive task benchmarking against the current ChatGPT desktop app and Claude Code application/CLI workflows.

### 3.2 Out of scope for v0.19 maintenance

- declaring Work or Cowork production-ready;
- cloud task execution parity;
- full desktop computer-use parity;
- macOS or Linux release qualification;
- comparing model intelligence using subjective prompts without fixed fixtures and scoring rules;
- changing engine behavior merely to increase coverage percentages.

### 4.2 Confirmed documentation defect

- `README.md` reported React 18 while `package.json` uses React 19.1.0. This plan corrects the public architecture table to React 19.

### 4.3 Confirmed evidence gaps

These are not automatically product bugs, but they prevent a professional release decision:

1. There is no `docs/golden-runs/v0.19.0.md` scorecard for the released Chat/Code boundary.
2. Pull-request CI does not execute a packaged desktop GUI journey.
3. The real-provider smoke depends on a local credentialed environment and is not deterministic enough to be the only end-to-end signal.
4. Installer and in-app upgrade E2E are release-machine procedures rather than a scheduled automated lane.
5. There is no committed performance baseline for startup, response latency, memory, long transcripts, or repository scale.
6. There is no committed accessibility matrix for keyboard-only use, focus order, screen-reader names, contrast, zoom, or reduced motion.
7. Competitive task results are not recorded with common fixtures, versions, timestamps, or scoring rules.
8. Historical roadmaps still contain pre-v0.19 product claims and must not be used as current acceptance evidence.

### 4.4 Items requiring re-verification

The dogfood log records these behaviors, but current v0.19 status is not proven. Each must be reproduced before it is called an open defect:

- stale Plan or Terminal panels after switching or creating sessions;
- Chinese IME conflicts in `@` suggestions and the command palette;
- global shortcuts not returning after an embedded preview receives focus;
- occasional empty review output;
- ambiguity when different catalog entries share the same provider model ID;
- line-number drift in review findings after the workspace changes.

## 5. Risk-based quality model

| Risk | Severity if escaped | Primary detector | Release rule |
|---|---:|---|---|
| Chat gains any local extension or executable capability | P0 | Lifecycle fan-out, restore, reload, subagent, hooks, MCP, LSP tests | Zero tolerance. |
| Wrong endpoint or credential receives a request | P0 | Dual-mock routing and restored-session identity tests | Zero tolerance. |
| Git/worktree operation targets the wrong repository or loses user work | P0 | Explicit-root fixtures, conflict injection, snapshot restore | Zero tolerance. |
| Update cannot complete, relaunch, or preserve state | P0 | Old-to-new packaged upgrade E2E | Zero tolerance. |
| Binding migration loses or silently reclassifies a session | P0 | Crash-window, concurrent migration, future-schema tests | Zero tolerance. |
| Approval or blocked-state parsing fails open | P0 | Malformed/future payload tests and UI denial tests | Zero tolerance. |
| Provider protocol drift breaks one supported backend | P1 | Compliance matrix and real-provider canary | No known P1 at release. |
| Cancel, interject, queue, or background work becomes unresponsive | P1 | Controlled slow-server and long-task tests | No known P1 at release. |
| UI state leaks between sessions or surfaces | P1 | Rapid-switch GUI E2E | No reproducible P1 at release. |
| Large repository or transcript becomes unusable | P1/P2 | Performance and soak suites | Must meet published budgets. |
| Accessibility blocks a keyboard or assistive-technology workflow | P1/P2 | Accessibility suite and manual audit | No critical path blocker. |

## 6. Test architecture

| Level | Purpose | Trigger | Examples |
|---|---|---|---|
| L0 Static | Reject malformed or inconsistent changes quickly | Every PR | TypeScript, build, Clippy, lock/version checks, diff checks. |
| L1 Unit/property | Prove pure rules and boundary values | Every PR | sidecar parser, capability gates, structured error parsing, path normalization. |
| L2 Protocol contract | Prove request/response shapes against deterministic mocks | Every PR | provider 4a/4b, SSE fragmentation, tool calls, error envelopes, ACP meta. |
| L3 Engine integration | Prove real session and tool lifecycles | Every PR | create/load, fan-out, subagents, worktrees, MCP, hooks, identity. |
| L4 Desktop E2E | Prove the packaged user journey and visible state | Nightly and RC | first run, Chat/Code switch, approvals, update, crash restore. |
| L5 Real-provider canary | Detect provider behavior not represented by mocks | Nightly/weekly, budgeted | one GLM, one DeepSeek, one generic compatible endpoint path. |
| L6 Security/chaos | Prove fail-closed behavior under hostile or interrupted conditions | Nightly and RC | corrupt files, plugin reload, network loss, process kill, disk full, future schemas. |
| L7 Dogfood/competitive | Measure product outcomes and friction | Weekly and RC | shared benchmark tasks, defect diary, recovery and UX scoring. |

No negative test may pass only because its fixture failed to activate. Each denial test must include a positive control proving that the same fixture works in an allowed Code session.

## 7. Environment matrix

### 7.1 Required environments

| Dimension | Required values |
|---|---|
| OS | Windows 11 current; Windows 10 final supported build for release candidates. |
| Install state | fresh install; current stable to candidate; previous two minor versions where migration changed. |
| Locale/input | English; Simplified Chinese; Microsoft Pinyin IME. |
| Display | 100%, 150%, and 200% scale; 1280x720 minimum; 1920x1080 reference. |
| Repository | tiny fixture; medium monorepo; 100k-file synthetic tree; path containing spaces and non-ASCII characters. |
| Provider | deterministic mock; GLM; DeepSeek; generic OpenAI-compatible endpoint. |
| Network | normal; 500 ms latency; disconnect; timeout; HTTP 401/403/429/5xx; malformed and truncated stream. |
| Credentials | absent; invalid; valid; rotated while app is running. |
| Session data | empty; legacy; large transcript; corrupt sidecar; future schema; missing asset. |

### 7.2 Test data rules

- Never use a developer's real repository for destructive tests.
- Every fixture uses isolated `GROK_HOME`, app-data, provider endpoint, Git repository, and temp directory.
- Secrets are injected through the test process or OS keyring fixture and never committed or logged.
- Every negative fixture has a positive control in the same test or suite.
- Cleanup is scoped by resolved absolute paths; a failed cleanup must leave evidence rather than broaden deletion.

## 8. Core release suites

### 8.1 Surface identity and Chat isolation — P0

| ID | Scenario | Pass criteria |
|---|---|---|
| SURF-001 | Create Chat | Engine handshake confirms local extensions disabled before the handle reaches the UI. |
| SURF-002 | Create Code | Full Code toolchain is present; Chat restrictions do not leak into Code. |
| SURF-003 | Restore both surfaces | Each session restores to its original immutable surface and current policy version. |
| SURF-004 | UI surface disagrees with binding | Binding wins; UI changes to the bound surface without widening access. |
| SURF-005 | Missing binding after migration marker | Only that session is blocked as `unbound_surface`; healthy sessions still open. |
| SURF-006 | Corrupt/future binding | Structured, user-visible block; no engine session is exposed. |
| SURF-007 | Concurrent first write | Exactly one identity wins; incompatible writer receives immutable conflict. |
| SURF-008 | Plugin reload/broadcast | Code remains functional; Chat registry, hooks, plugin MCP, skills, commands, LSP, and subagents remain empty. |
| SURF-009 | Restore/reconnect conflict | Conflict is rejected before MCP, hooks, permissions, or registry side effects. |
| SURF-010 | Hostile repository | `.mcp.json`, hooks, plugins, LSP, skills, symlinks, and instructions cannot activate in Chat. |
| SURF-011 | Provider request body | Chat request tools are exactly the approved built-in web tools; Code retains coding tools. |
| SURF-012 | Chat file/command attempt | No file, terminal, Git, or custom MCP request is emitted; refusal is visible and attributable. |

### 8.2 Provider and multimodal compatibility — P0/P1

| ID | Scenario | Pass criteria |
|---|---|---|
| PROV-001 | Catalog selection | Only the selected entry's endpoint and credential receive a request. |
| PROV-002 | Duplicate model IDs | Catalog key remains authoritative; restore never crosses entries. |
| PROV-003 | Hot switch | Model changes without restart and subsequent request identity is correct. |
| PROV-004 | Stream fragmentation | Text, reasoning, tool arguments, finish reasons, usage, and errors parse across arbitrary chunk boundaries. |

## 10. Exploratory bug-hunt charters

1. **Mixed-surface lifetime:** keep Chat and Code alive on one engine connection while repeatedly reloading plugins, MCP, hooks, models, and sessions.
2. **Crash-window migration:** terminate the app between every step of engine create, sidecar write, marker publication, and UI exposure.
3. **Provider identity drift:** reuse model IDs across providers, rotate credentials, hot reload, restore legacy sessions, and switch rapidly.
4. **State leakage:** alternate sessions and surfaces during streaming, approvals, terminal output, plan mode, review, and Git refresh.
5. **Hostile project:** add malformed configs, prompt-injection documents, symlinks/junctions, long paths, nested repos, huge files, and executable hooks.
6. **Network chaos:** disconnect during SSE, MCP initialize, tool result, updater download, and installer handoff.
7. **Human-input stress:** Chinese IME, paste images/files, keyboard repeat, double clicks, cancellation races, and focus changes.
8. **Resource pressure:** 100k files, 10k Git changes, long transcripts, low disk, constrained memory, and many child processes.

Every charter produces a session note containing build SHA, environment, timeline, evidence, suspected invariant, minimal reproduction, and cleanup confirmation.

## 11. Defect model and triage

### 11.1 Severity

| Level | Definition | Examples | Release treatment |
|---|---|---|---|
| P0 Critical | Security boundary bypass, credential leak, data loss, wrong repository/provider, unrecoverable update | Chat executes local hook; discard hits another repo | Stop release; immediate owner. |
| P1 High | Core workflow blocked or incorrect with no safe workaround | cannot restore sessions; cancel leaves task running | Fix before release. |
| P2 Medium | Important degradation with a safe workaround | panel stale until reopen; provider error unclear | Ship only with explicit owner and target. |
| P3 Low | Cosmetic, low-frequency, or minor friction | spacing, non-critical copy | Backlog by product value. |

### 11.2 Required defect evidence

- product version and commit SHA;
- surface, session ID, provider catalog key, and workspace fixture;
- exact preconditions and minimal reproduction;
- expected and actual behavior;
- user/data/security impact;
- logs, screenshots/video, request transcript, filesystem or Git assertions;
- recovery behavior and cleanup result;
- first bad/last good version when known;
- regression test required to close P0/P1 defects.

Use [the defect report template](defect-report-template.md). A defect is not closed by a code change alone; the discriminating regression must fail on the old behavior and pass on the fix.

## 13. Release gates

### 13.1 Every pull request

- frontend typecheck, tests, and production build;
- Rust Clippy, unit tests, canaries, provider contracts, surface contracts, and effective-tree audit;
- changed-risk test selection plus mandatory P0 suite for surface/provider/update changes;
- no unexplained snapshot, lock, manifest, or evidence drift;
- a regression test for every fixed P0/P1.

### 13.2 Nightly

- packaged Windows desktop E2E on an isolated VM;
- deterministic mock-provider core journeys;
- real-provider budgeted canaries;
- network chaos, large transcript/repository, cancellation, and process cleanup;
- accessibility scan and keyboard smoke;
- old-stable-to-main updater dry run or isolated installation run;
- flake and performance trend publication.

### 13.3 Release candidate

- full environment matrix and a completed [release scorecard](release-scorecard-template.md);
- v0.19+ golden tasks with fresh evidence, not inherited assumptions;
- competitive benchmark subset B01–B07;
- 48-hour dogfood soak with no unresolved P0/P1;
- signed installer, MSI, updater manifest, direct/mirror hash, and rollback verification;
- explicit product, engineering, and quality go/no-go sign-off.

## 14. Development support roadmap

### Sprint 0 — Evidence foundation (one week)

1. Create `docs/golden-runs/v0.19.0.md` from fresh runs; do not backfill with “expected pass.”
2. Add stable data-test identifiers to critical desktop controls.
3. Build deterministic mock-provider GUI journeys for first run, Chat, Code, approval, restore, and surface conflict.
4. Capture cold start, idle memory, 100-turn session, and 100k-file repository baselines.
5. Start a machine-readable defect ledger with component, severity, found-by, escaped version, and regression test.

### v0.19.1 — Surface and UX hardening

1. Automate SURF-001–012 through backend and packaged GUI layers.
2. Re-verify all dogfood items in section 4.4 and convert reproducible cases into issues/tests.
3. Add Chinese IME, keyboard-only, focus restoration, session-panel isolation, and DPI coverage.
4. Add slow/disconnected provider behavior and user-facing retry diagnostics.
5. Ship no new surface; reduce uncertainty in the released contract.

### v0.19.2 — Reliability and update automation

1. Schedule isolated installer/update E2E for supported version pairs.
2. Add crash-window and disk-full fault injection for bindings, session persistence, downloads, and install handoff.
3. Add long-session, large-repository, resource, and cancellation soak suites.
4. Publish performance and flake trends as CI artifacts.

### v0.20 — Differentiation, not imitation

1. Publish a provider compatibility scorecard and guided diagnostics for failed endpoints.
2. Improve evidence-first review, diff anchoring, and safe worktree delivery.
3. Evaluate browser-assisted local preview against B10 without promising full desktop computer use.
4. Begin Work only after document citation, prompt-injection, read-only source, and export gates are automated.
5. Begin Cowork only after its declared isolation tier is testable; Git worktree isolation must never be presented as filesystem sandboxing.

## 16. Evidence artifacts

Each release stores:

- test plan revision and product SHA;
- automated job URLs and artifact hashes;
- golden-task scorecard;
- environment and provider matrix;
- performance/flake trends;
- competitive task scorecard;
- open-defect waiver list, if any;
- signed installer/update verification;
- final go/no-go decision and approvers.

Evidence must be durable in the repository or release record. Expiring CI artifacts alone are not sufficient for a release claim.
