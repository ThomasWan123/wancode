# v0.23.3 interaction information architecture

Status: implementation baseline for the first increment of the Chat / Code /
Work interaction refresh.

## 1. Problem statement

WanCode currently renders `Compact / Quiet / Verbose` beside the permission
control in every composer. Those options only hide or expand transcript detail,
but their location and names imply that they change model behavior, answer
length, execution policy, or context. `Compact` also collides with the existing
context-compaction action and `/compact` command.

The three surfaces correctly share one conversation engine and composer shell.
They must not, however, present identical affordances or language when their
jobs differ.

## 2. Benchmark-derived decisions

This is a principles comparison, not a pixel-for-pixel clone:

| Product signal | What is worth absorbing | WanCode decision |
| --- | --- | --- |
| Claude Code exposes plan/permission mode separately from verbose diagnostics | Safety state and diagnostic visibility are different controls | Keep permission beside Send; move transcript detail into the message region |
| ChatGPT Projects keeps uploaded project sources as durable context and opens richer authoring in a separate workspace | Source context, conversation, and artifact editing need distinct homes | Work owns project sources; future artifact preview/editor belongs beside the transcript, not inside the composer |
| Codex models planning, sandbox/approval, reasoning visibility, and context compaction as separate configuration concepts | Operational state must not be compressed into one ambiguous mode selector | Use five explicit product layers and preserve their independent state |
| Open-source agent harnesses expose structured tool events and terminal outcomes | Agent activity should be inspectable without flooding the normal answer | Standard collapses activity; Debug reveals provider-available summaries and tool diagnostics |

Primary references used for this baseline:

- Claude Code CLI reference: <https://docs.anthropic.com/en/docs/claude-code/cli-usage>
- ChatGPT Projects: <https://help.openai.com/en/articles/10169521-projects-in-chatgpt>
- Codex plan-mode contract: <https://github.com/openai/codex/blob/main/codex-rs/collaboration-mode-templates/templates/plan.md>
- Codex configuration schema: <https://github.com/openai/codex/blob/main/codex-rs/core/config.schema.json>

## 3. Product layers

These five dimensions are independent and must remain visibly separate:

1. **Surface** — Chat / Code / Work determines the task workspace and tool set.
2. **Execution phase** — ask / plan / act / review describes task lifecycle.
3. **Permission boundary** — approval mode controls which actions may run.
4. **Message display** — minimal / standard / debug controls rendered detail only.
5. **Context management** — usage, automatic compaction, and manual compaction.

No display preference may modify a request, model setting, permission, persisted
conversation, or context budget.

## 4. v0.23.3 implementation

### Message display

- Remove the three-way display control from the composer.
- Add a low-emphasis `View` menu to the message region.
- Use `Minimal / Standard / Debug` (`精简 / 标准 / 调试`).
- Default to Standard.
- Persist the preference at user level.
- Migrate legacy values without changing effective behavior:
  `compact -> minimal`, `default|quiet -> standard`, `verbose -> debug`.
- State explicitly that the preference changes display only.

### Surface-specific composer language

- Chat invites a general question and image attachment.
- Code invites a coding task and file mentions.
- Work invites questions about project sources and document mentions.
- The permission control remains next to Send because it changes execution risk.

### Context terminology

- English UI uses `Compress context`; `/compact` remains the compatible command.
- Context controls remain in the context meter, never in message display settings.

### Process disclosure

- UI labels provider-visible process content as `Process summary`, not a promise
  of complete hidden chain-of-thought.
- Debug expands available summaries and tool diagnostics. It does not request
  more reasoning from the model.

## 5. Acceptance criteria

1. A fresh install uses Standard display.
2. Every legacy preference maps to the same effective visibility after upgrade.
3. Minimal hides process summaries, change-review chips, and tool output while
   retaining tool status and final messages.
4. Standard shows summaries with details collapsed.
5. Debug expands available process and tool detail.
6. Changing the display creates no backend invocation and changes no composer
   payload, model, permission, context counter, or session identity.
7. The View menu is keyboard accessible and exposes menu/radio state.
8. Chat, Code, and Work render distinct task placeholders.
9. Chinese and English terminology carry the same semantics.
10. Frontend tests, production build, and packaged-GUI smoke evidence are bound
    to the reviewed head; anything not run is reported as NOT-RUN.

## 6. Executable delivery plan

| Increment | Deliverable | Required evidence | Release gate |
| --- | --- | --- | --- |
| v0.23.3 | Correct control placement, terminology, migration, and surface prompts | Legacy mapping tests; message-view behavior and keyboard tests; i18n parity; production build; packaged GUI smoke | Independent review of the exact head, then separate merge and release authorization |
| v0.24.0 | Structured activity timeline and explicit Plan -> Act -> Review lifecycle | Event-order/terminal-state tests; cancellation and approval chaos cases; Windows packaged end-to-end run | No ambiguous or duplicate terminal state; recovery preserves task ownership |
| v0.24.x | Code result panel and Work source/artifact panel | Diff/test/terminal integration tests; source citation and document preview matrix | Every result links back to its source or execution evidence |
| v0.25.0 | Provider/parser/tool/skill/MCP plugin contracts and resumable background work | Compatibility fixtures; plugin isolation; crash/restart/reconnect matrix; quota and timeout containment | Fail-closed capability negotiation and deterministic recovery |

Execution rules for every increment:

1. Bind design, implementation, tests, and CI evidence to one exact head SHA.
2. Keep permission, context, and display state in separate types and storage keys.
3. Treat Windows packaged behavior as a release requirement; mark unavailable
   environments `NOT-RUN` rather than inferring success from unit tests.
4. Require independent review before merge. Version bumps, tags, assets, updater
   manifests, and release publication remain separately authorized operations.
