# `local_extensions_disabled` 接口草案（v0.19 · G26 唯一安全例外）

> 状态：**第三版草案待评审，尚未改动 fork**。依据 = 设计稿第五版 §1.3 的裁决与
> 2c 探针实证（`docs/evidence/v019-2c-fanout-probe.log`）。
> 本文锁定边界后再开 fork 主题 PR。

## 1. wire 字段位置与默认值（第三版：**推翻第二版归宿**）

### 1.0 第二版的 P0 错误与实证

第二版把标志放进 `StartupHints`，理由是"它已从 meta 解析、存在 actor 上、
只读"。**这是错的**——实测 `spawn_and_register_session`
（`agent_ops.rs:2864`）解析 startupHints 用的是 `init.meta`，而 `init`
来自 `self.initialize_request`（`acp_agent.rs:818` 取自 `OnceCell`，
`acp_agent.rs:141` 每连接只 `set` 一次）：

```rust
// acp_agent.rs:818 —— 连接级，不是会话级
let init = self.initialize_request.get().ok_or_else(|| …)?;
// agent_ops.rs:2972
let startup_hints = init.meta.as_ref().and_then(|m| m.get("startupHints"))…
```

**后果**：`StartupHints` 是**每连接一份**。而本项目的真实拓扑正是
**单连接内 Chat + Code 并存**（2c 探针即如此，生产 WanCode 也共用一个
引擎连接）——放这里会导致同连接两个会话共享同一个值：要么两层都禁用
（Code 废掉），要么都不禁用（Chat 裸奔）。按第二版实现出来的接口
**在真实拓扑下根本不成立**。

### 1.1 第三版归宿：会话级 `session_meta`

`spawn_and_register_session` **同时**收到 `init`（连接级）与
`session_meta`（本次 New/Load 的 meta）；后者已被多处按会话消费：
`reject_direct_hub_cloud_meta(session_meta)`（:2899）、
`parse_agent_profile_from_meta(session_meta)`（:3181）。标志走它。

**wire**：`_meta["x.ai/localExtensionsDisabled"] = true`（顶层键，与
`x.ai/mcp/servers`、`agentProfile` 同级；不塞进 `startupHints`，避免与
连接级语义混淆）。

```rust
// agent_ops.rs：与既有 session_meta 解析并列
let local_extensions_disabled =
    parse_local_extensions_disabled(session_meta)?;   // 类型错误 → Err（T11）
```

| 路径 | 载体 | 说明 |
|---|---|---|
| 新建 | `NewSessionRequest._meta["x.ai/localExtensionsDisabled"]` | Chat 显式传 `true` |
| 恢复 | `LoadSessionRequest._meta["x.ai/localExtensionsDisabled"]` | 客户端按 sidecar binding 重传 |

默认（键缺失）= `false`：其他客户端与 Code 路径逐字保持现状。

> 引擎**不持久化**该标志（沿用第二版裁决）：恢复时由客户端按
> `SurfaceBinding.surface_kind == Chat` 重传，与 `EffectiveSurfacePolicy`
> 每次派生同源；漏传由握手回显（§3）兜住。

## 2. 会话内不可变锁存

- 锁存位置：**新增会话级只读字段**——`SessionActor.local_extensions_disabled: bool`
  与 `SessionHandle.local_extensions_disabled: bool`（后者供 Load 冲突比较与
  握手取值，见 §3/T8/T9）。**不复用 `StartupHints`**（连接级，见 §1.0）。
- 不可变性：只在 actor 构造时写入；不新增 setter；`SessionCommand` 不加切换变体。
- 恢复重建：Load 走同一 `spawn_and_register_session`；**若 session 已有驻留
  actor**，先比较 `SessionHandle` 上的锁存值（§3 时序），不一致即拒绝，
  不重建、不就地改。

## 3. 应用确认握手（防静默 fail-open）

引擎在**两个响应**里回显，位置与既有 meta 同处：

| 响应 | 位置 | 值 |
|---|---|---|
| `NewSessionResponse` | `.meta["localExtensionsDisabledApplied"]` | 请求为 true 且策略已装配 → `true` |
| `LoadSessionResponse` | 同上（`agent_ops.rs` 现有 `response_meta` 构造处） | 同上 |

**取值来源（T12）**：`applied` 必须读**实际锁存状态**——新建取新 actor 的
字段，Load 取 `SessionHandle.local_extensions_disabled`；**不得**把请求值
原样回显，否则装配失败时会给出假确认。

**驻留 Load 的比较时序（第三版新增，T8/T9）**：对已有驻留 actor 的
`session_id`，比较必须发生在**任何 reconnect 副作用之前**——即在 MCP
重注册、client-hooks 装载、YOLO/权限模式重置等动作**之前**读
`SessionHandle` 的锁存值并判定；不一致立即返回
`{code:"local_extensions_disabled", policy:"local_extensions_disabled",
reason:"immutable_conflict"}`，**不执行任何副作用**。否则"先改状态再发现
冲突"会留下半改过的会话。

**WanCode 侧硬门**：`start_inner` 的 Chat 分支在拿到响应后立即校验——
字段缺失、为 `false`、或类型不符 ⇒ `cancel.cancel()`、**不安装 handle**、
返回结构化 `SURFACE_POLICY_BLOCKED{code: local_extensions_not_applied}`。
旧引擎（无此字段）因此**自动 fail-closed**，不会让 Chat 在"以为受保护"
的状态下运行。

|---|---|---|---|
| ① | 初始 discovery | `spawn.rs:1056` 一带的 hook registry 构建；plugin registry 初始化（`agent_ops.rs:303` 的共享快照读取） | 标志为真 ⇒ 跳过磁盘 hooks discovery、注入空 plugin registry |

| ⑤ | ACP 扩展 | `extensions/plugins.rs`（`x.ai/plugins/action`、`/list`）、`extensions/hooks.rs`（`x.ai/hooks/action`、`/list`）、`session_admin.rs`（`x.ai/plugins/reload`） | action 类结构化拒绝；list 类见 §5 |

**拒绝的错误形状**（统一）：`acp::Error::invalid_request()` +
`data = {"code":"local_extensions_disabled","policy":"local_extensions_disabled"}`。

> 第二版修订：**不写 `"surface":"chat"`**——引擎只知道自己被设了一个
> 策略位，不知道也不应假装知道 WanCode 的层命名。层名是客户端概念，
> 泄漏进引擎错误体会让引擎与客户端的分层词汇耦合。

## 5. 两个 list 的固定返回形状

禁用会话中恒为空，且**不是错误**（UI 可正常渲染空态）：

**必须沿用现有 DTO 的真实序列化**，不另造 wire 形状——
`HooksListResponse.load_errors` 带 `skip_serializing_if = "Vec::is_empty"`
（`xai-hooks-plugins-types/src/lib.rs:218`），空时**不出现在 wire 上**：

```json
// x.ai/plugins/list  →  PluginsListResponse { plugins: vec![] }
{"plugins": []}
// x.ai/hooks/list    →  HooksListResponse { hooks: vec![], project_trusted: false, load_errors: vec![] }
{"hooks": [], "projectTrusted": false}
```

实现要求：禁用分支**构造既有 DTO 再走同一 `to_ext_response`**，
不得手写 JSON 字面量——否则一旦上游给 DTO 加/改字段，禁用路径会与
正常路径产生形状分歧（第二版修订）。

理由：探针与 UI 都用"空数组"作为正证据；返回错误会迫使调用方区分
"禁用"与"故障"，反而更易 fail-open。

**整体零贡献要求（第三版）**：标志为 true 时，插件贡献的
**hooks / MCP / LSP / skills / commands 必须整体为零**——不是只把两个
list 清空。`PluginManifest` 除 hooks/mcp_servers 外还有 `lsp_servers`
（manifest.rs:169）与 skills/agents 贡献面，任一遗漏都是注入口。
Code 对照会话必须**全部仍可用**（T5 逐项相等）。

## 6. Code 默认路径逐项零变化

`local_extensions_disabled == false`（默认）时：

- `StartupHints` 多一个 `#[serde(default)]` bool，旧 meta 反序列化行为不变；
- 六个拦截点全部是 `if hints.local_extensions_disabled { … }` 的早退分支，
  false 分支**逐字走原路径**；
- 两个响应多一个 meta 键（旧客户端忽略未知键）；
- **验收**：Code 会话的 `plugins/list`、`hooks/list`、命令列表、hook 派发、
  MCP 合并与改动前逐项相等（引擎测试矩阵 §7 的 T5 覆盖）。

## 11. 客户端 preflight 的降级（本次裁决的直接推论）

**问题**：现有 `enforce_chat_plugin_preflight` 会在"机器上存在供 Code
使用的插件"时阻塞 Chat 启动。接口落地后这是**过度阻塞**——生命周期
隔离已由引擎硬门负责，Chat 不该因为别的层要用插件而开不起来。

**调整**：

**只降级两项**（第二版修订：降级范围必须精确，不能顺手把无关硬门一起降）：

| 客户端门 | 处置 | 理由 |
|---|---|---|
| `enforce_chat_plugin_preflight`（插件来源扫描） | **降为诊断日志** | 生命周期隔离已由引擎硬门 ①②③ 负责；不该因机器上有供 Code 用的插件就拦住 Chat |
| `ensure_no_disk_global_hooks`（磁盘 hooks 扫描） | **降为诊断日志** | 由引擎硬门 ①⑥ 覆盖 |

**以下仍是独立硬门，一律保留阻断语义**：

- **managed MCP 实例级关闭**（`apply_chat_agent_config_overrides`：
  `managed_mcps_enabled=false` + `managed_mcp_gateway_tools_enabled=false`）
  ——managed MCP 不经插件路径，引擎硬门不覆盖；
- **空 client MCP**（`NewSessionRequest.mcp_servers = []`）——客户端自己
  传入的 MCP 与插件无关；
- **Chat profile 工具裁剪**（`_meta.agentProfile` 的最小 tool_config +
  五关闭项 + hosted allowlist）——这是工具面的主防线，与本接口正交；
- **`ensure_chat_model_allowed`**（agent_type 冲突门）——防 profile 被
  strict harness 压过，引擎硬门不覆盖。

**marketplace 自动安装 / 远程 plugin settings：不保留客户端阻断**
（第三版裁决）。它们最终都只是**共享 plugin registry 的来源**；只要禁用
会话在初始构建、派生能力、broadcast、snapshot 四层都不消费该 registry，
就注入不到 Chat。

**承诺口径必须精确**：对外表述为「**Chat 会话不加载或执行本地扩展**」，
**不得**扩大为「共享引擎进程绝不安装插件或写插件存储」——同进程的 Code
会话仍可合法触发全局安装，那是它的正当能力。

**遗漏的独立客户端硬门（第三版新增）**：`_meta["x.ai/mcp/servers"]` 经
`parse_acp_mcp_servers(session_meta)` 注册 **ACP MCP**，它与
`NewSessionRequest.mcp_servers` 是**两条不同的路径**。Chat 会话构造器
