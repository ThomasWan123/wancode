# `local_extensions_disabled` 接口草案（v0.19 · G26 唯一安全例外）

> 状态：**草案待评审，尚未改动 fork**。依据 = 设计稿第五版 §1.3 的裁决与
> 2c 探针实证（`docs/evidence/v019-2c-fanout-probe.log`）。
> 本文锁定边界后再开 fork 主题 PR。

## 1. wire 字段位置与默认值

**归宿：`StartupHints`**（`session/acp_types.rs:591`）。选它而非新造结构，
理由是它已经具备本接口需要的三个性质，且是 new/load 共用路径：

- 从 meta 解析：`spawn_and_register_session`（`agent_ops.rs:2972`）读
  `init.meta["startupHints"]`，`serde_json::from_value` 失败即
  `unwrap_or_default()`；
- 存进 session actor：`acp_session.rs:643 pub(crate) startup_hints: StartupHints`；
- 会话内只读：现有代码只读不写（`prompt_build.rs:364/370`、
  `hook_dispatch.rs:187` 等）。

```rust
pub struct StartupHints {
    #[serde(default)] pub non_interactive: bool,
    #[serde(default)] pub skip_git_status: bool,
    /// v0.19：禁用该会话的一切**本地扩展**——插件与可执行磁盘 hooks。
    /// 默认 false：其他客户端与 Code 路径逐字保持现状。
    #[serde(default)] pub local_extensions_disabled: bool,
    // …既有字段不动
}
```

**两条输入路径**（共用同一解析点，无需分别接线）：

| 路径 | 载体 | 说明 |
|---|---|---|
| 新建 | `NewSessionRequest._meta.startupHints.localExtensionsDisabled` | Chat 显式传 `true` |
| 恢复 | `LoadSessionRequest._meta.startupHints.localExtensionsDisabled` | **由客户端按 sidecar binding 重传** |

> 恢复语义（与 WanCode 侧 §0.1 契约一致）：引擎**不持久化**该标志，
> 每次 Load 由客户端依据 `SurfaceBinding.surface_kind == Chat` 重新传入。
> 这样引擎侧无新增持久化状态，也避免"磁盘上的权限快照"——与
> `EffectiveSurfacePolicy` 每次派生的设计同源。
> 代价：客户端漏传 = 会话按 Code 语义跑；由**握手回显**（§3）兜住。

## 2. 会话内不可变锁存

- 锁存位置：`SessionActor.startup_hints`（已有字段），随 actor 生命周期存在；
- 不可变性：不新增任何 setter；`SessionCommand` 不增加切换变体；
- 恢复重建：Load 走同一 `spawn_and_register_session`，新 actor 用新传入的
  hints 重建——**不存在运行中切换**，只有"新 actor 用新值"。

## 3. 应用确认握手（防静默 fail-open）

引擎在**两个响应**里回显，位置与既有 meta 同处：

| 响应 | 位置 | 值 |
|---|---|---|
| `NewSessionResponse` | `.meta["localExtensionsDisabledApplied"]` | 请求为 true 且策略已装配 → `true` |
| `LoadSessionResponse` | 同上（`agent_ops.rs` 现有 `response_meta` 构造处） | 同上 |

**WanCode 侧硬门**：`start_inner` 的 Chat 分支在拿到响应后立即校验——
字段缺失、为 `false`、或类型不符 ⇒ `cancel.cancel()`、**不安装 handle**、
返回结构化 `SURFACE_POLICY_BLOCKED{code: local_extensions_not_applied}`。
旧引擎（无此字段）因此**自动 fail-closed**，不会让 Chat 在"以为受保护"
的状态下运行。

## 4. 六面拦截点

| # | 面 | 拦截点 | 行为 |
|---|---|---|---|
| ① | 初始 discovery | `spawn.rs:1056` 一带的 hook registry 构建；plugin registry 初始化（`agent_ops.rs:303` 的共享快照读取） | 标志为真 ⇒ 跳过磁盘 hooks discovery、注入空 plugin registry |
| ② | broadcast | `broadcast_plugin_registry_to_sessions`（`mvp_agent/mod.rs`） | 遍历时**跳过**该会话，不发 `ReloadPlugins` |
| ③ | snapshot 防线 | `apply_plugin_registry_snapshot`（`hooks_plugins.rs:832/902`） | 即使误收到，也强制置空并早退（第二道防线，②失效时兜底） |
| ④ | reload / slash | `slash_exec.rs` 的 `/plugins`、`/reload-plugins`、`/hooks`；`BuiltinGate::Plugins` 的派生 | 命令不出现在可用列表；即便被直接调用也结构化拒绝 |
| ⑤ | ACP 扩展 | `extensions/plugins.rs`（`x.ai/plugins/action`、`/list`）、`extensions/hooks.rs`（`x.ai/hooks/action`、`/list`）、`session_admin.rs`（`x.ai/plugins/reload`） | action 类结构化拒绝；list 类见 §5 |
| ⑥ | hooks / plugin MCP | hook dispatch（`turn.rs:784` 的派发点）；plugin MCP 合并（`hooks_plugins.rs:902`） | 不派发任何 hook；不合并 plugin MCP、不建连 |

**拒绝的错误形状**（统一）：`acp::Error::invalid_request()` +
`data = {"code":"local_extensions_disabled","surface":"chat"}`，
让客户端能区分"功能不存在"与"本会话被策略禁用"。

## 5. 两个 list 的固定返回形状

禁用会话中恒为空，且**不是错误**（UI 可正常渲染空态）：

```json
// x.ai/plugins/list
{"plugins": []}
// x.ai/hooks/list
{"hooks": [], "projectTrusted": false, "loadErrors": []}
```

理由：探针与 UI 都用"空数组"作为正证据；返回错误会迫使调用方区分
"禁用"与"故障"，反而更易 fail-open。

## 6. Code 默认路径逐项零变化

`local_extensions_disabled == false`（默认）时：

- `StartupHints` 多一个 `#[serde(default)]` bool，旧 meta 反序列化行为不变；
- 六个拦截点全部是 `if hints.local_extensions_disabled { … }` 的早退分支，
  false 分支**逐字走原路径**；
- 两个响应多一个 meta 键（旧客户端忽略未知键）；
- **验收**：Code 会话的 `plugins/list`、`hooks/list`、命令列表、hook 派发、
  MCP 合并与改动前逐项相等（引擎测试矩阵 §7 的 T5 覆盖）。

## 7. 引擎测试矩阵（fork PR 内）

| # | 场景 | 断言 |
|---|---|---|
| T1 | 新建 + 标志 true | registry 空、hooks 空、两 list 空、握手回显 true |
| T2 | 恢复 + 标志 true | 同 T1；且**不依赖任何持久化**（引擎侧无该字段落盘） |
| T3 | **广播污染** | 另一会话触发 `x.ai/plugins/action{Reload}` 后，禁用会话 registry 仍空、零 hook 派发 |
| T4 | 显式 reload | 禁用会话调 `/plugins reload` 与 ACP reload 均结构化拒绝，registry 不变 |
| T5 | **Code/Chat 并存** | 同进程内 Code 会话行为与改动前逐项相等（registry/hooks/list/命令/派发/MCP） |
| T6 | 旧客户端兼容 | 不传该字段 ⇒ 默认 false ⇒ 全部现状行为；响应仍带 applied=false 或不带（二选一，本 PR 定为**不带**，见下） |
| T7 | 握手缺失 | 请求 true 但装配失败（构造异常路径）⇒ **不得**回显 applied=true |

> T6 的取舍：请求为 false 时**不回显**该 meta 键——避免给旧客户端引入
> 新语义。WanCode 只在 Chat 分支要求 `applied == true`，Code 分支不看。

## 11. 客户端 preflight 的降级（本次裁决的直接推论）

**问题**：现有 `enforce_chat_plugin_preflight` 会在"机器上存在供 Code
使用的插件"时阻塞 Chat 启动。接口落地后这是**过度阻塞**——生命周期
隔离已由引擎硬门负责，Chat 不该因为别的层要用插件而开不起来。

**调整**：

- `enforce_chat_plugin_preflight` 从**启动阻断门**降为**诊断日志**
  （记录检测到的来源，不阻断）；
- 仅保留引擎硬门**尚未覆盖**的来源检查作为阻断项——按 §4 六面梳理后，
  当前预期为**空集**（六面已覆盖插件与磁盘 hooks 的全部注入路径）；
  若评审认为仍有遗漏面，在此列出并保留其阻断语义；
- `ensure_no_disk_global_hooks` 同样降级（磁盘 hooks 由 ①⑥ 覆盖）；
- **保留** `ensure_chat_model_allowed`（agent_type 冲突门）——它与插件
  无关，防的是 profile 被 strict harness 压过，引擎硬门不覆盖。

> 净效果：Chat 的安全承诺从"启动前扫描 + 客户端裁剪"改为"引擎会话级
> 硬门 + 客户端工具裁剪"，前者的误伤消失，后者的强度提升。
